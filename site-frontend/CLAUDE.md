# Grupo Dimensão — Engineering & AI Development Guide

## 1. Contexto do projeto

Este repositório contém o novo website institucional do Grupo Dimensão.

O Grupo Dimensão atua principalmente com:

- Portaria e Controle de Acesso
- Portaria Remota
- Sistemas de Segurança Eletrônica
- Vigilância Patrimonial
- Conservação Patrimonial

A empresa atende diferentes segmentos, incluindo:

- Condomínios residenciais
- Indústrias
- Empresas
- Restaurantes
- Hospitais
- Comércios

A empresa possui atuação em São Paulo e Mato Grosso do Sul.

O website tem como objetivos principais:

1. Apresentar a empresa.
2. Apresentar seus serviços.
3. Demonstrar autoridade, experiência e estrutura.
4. Gerar pedidos de orçamento.
5. Gerar contatos comerciais.
6. Direcionar usuários para WhatsApp.
7. Apresentar notícias e conteúdos.
8. Permitir gerenciamento de conteúdo pelo CMS.
9. Permitir que marketing altere conteúdos sem modificar código.

# 13. Animações

O site deve combinar três níveis de animação:

### Sutil

- fade;
- reveal;
- microinterações;
- transições.

### Moderado

- scroll animations;
- parallax;
- hover sofisticado;
- imagens reveladas;
- contadores.

### Experiência

- transições entre seções;
- timelines;
- composição cinematográfica;
- elementos interativos.

A animação nunca deve prejudicar:

- performance;
- acessibilidade;
- legibilidade;
- conversão;
- navegação.

Respeitar `prefers-reduced-motion`.

Não adicionar animação simplesmente porque é tecnicamente possível.

---

# 14. Motion e GSAP

O projeto já utiliza Motion e GSAP.

Não adicionar outra biblioteca de animação sem justificativa explícita.

Preferências:

### Motion

Utilizar para:

- componentes React;
- reveals;
- fades;
- hover;
- microinterações;
- animações de entrada;
- transições simples.

### GSAP

Utilizar quando houver necessidade de:

- timelines complexas;
- scroll-driven animation;
- parallax avançado;
- sequências cinematográficas;
- animações coordenadas.

Não utilizar Motion e GSAP simultaneamente para resolver o mesmo problema sem necessidade.

# 15. Responsividade

A prioridade é:

1. Mobile
2. Notebook
3. Desktop

Mobile não deve ser tratado simplesmente como desktop reduzido.

O design deve ser adaptado para cada breakpoint.

Verificar especialmente:

- espaçamento;
- tipografia;
- altura do Hero;
- navegação;
- imagens;
- animações;
- CTA;
- cards;
- grids;
- overflow horizontal.

Nunca aceitar overflow horizontal acidental.

---

# 16. Performance

Performance é prioridade.

Preferir:

- Server Components;
- carregamento sob demanda;
- imagens otimizadas;
- `next/image`;
- lazy loading;
- `transform` e `opacity` para animações;
- redução de JavaScript no cliente;
- componentes Client apenas quando necessário.

Evitar:

- grandes bundles desnecessários;
- animações que utilizem propriedades caras;
- imagens gigantes sem otimização;
- bibliotecas adicionais sem necessidade;
- efeitos contínuos que consomem CPU.

Não transformar uma seção puramente visual em Client Component sem necessidade.

---

# 17. Server Components / Client Components

Preferir Server Components por padrão.

Utilizar `"use client"` somente quando necessário para:

- estado;
- eventos;
- APIs do browser;
- animações/interações que realmente exigem cliente;
- componentes interativos.

Antes de transformar um componente em Client Component, verificar se existe uma alternativa Server Component.

---

# 18. CMS

O projeto possui um CMS dentro do mesmo repositório.

O CMS deve permitir que usuários autorizados gerenciem conteúdo sem editar código.

Conteúdos que devem ser administráveis:

- banners;
- textos;
- imagens;
- serviços;
- notícias;
- estatísticas;
- certificações;
- conteúdos institucionais;
- SEO quando aplicável.

O marketing não deve precisar modificar código para alterar conteúdo editorial.

---

# 19. CMS versus código

O CMS controla:

- conteúdo;
- imagens;
- textos;
- dados;
- serviços;
- notícias;
- banners;
- informações editoriais.

O código controla:

- layout;
- arquitetura;
- componentes;
- design system;
- animações;
- responsividade;
- UX;
- regras técnicas.

Não criar um page builder genérico sem necessidade.

---

# 20. Serviços dinâmicos

A arquitetura deve permitir futuramente criar novos serviços pelo CMS.

Preferir:

/servicos/[slug]

em vez de criar uma página React manual para cada serviço.

Adicionar um novo serviço deve significar:

1. cadastrar no CMS;
2. adicionar conteúdo;
3. adicionar imagens;
4. publicar.

Não deve ser necessário criar uma nova página de código para cada novo serviço.

# 21. Banco de dados

A implementação atual utiliza SQLite com Drizzle.

Decisão atual:

- manter SQLite inicialmente;
- não migrar para MySQL sem necessidade comprovada.

A presença de MySQL na infraestrutura de hospedagem não é motivo suficiente para realizar uma migração.

Antes do deploy definitivo verificar:

- persistência;
- backup;
- restauração;
- concorrência;
- execução do processo Node;
- scheduler;
- segurança dos arquivos.

5. verificar persistência;

# 28. Git

O projeto utiliza somente a branch `main`.

Não utilizar GitFlow.

Não criar branches automaticamente.

Claude deve trabalhar diretamente na `main`.

Antes de alterações importantes:

1. verificar `git status`;
2. verificar alterações existentes;
3. não sobrescrever trabalho não commitado;
4. não executar comandos destrutivos sem autorização.

Não executar automaticamente:

- `git reset --hard`;
- `git clean -fd`;
- remoção em massa;
- force push;
- alteração destrutiva de histórico.

# 33. Qualidade de código

Priorizar:

- código simples;
- componentes reutilizáveis;
- nomes claros;
- baixo acoplamento;
- separação de responsabilidades;
- tipagem forte;
- ausência de duplicação desnecessária.

Não abstrair prematuramente.

Uma abstração deve resolver um problema real.

# 34. Critérios para considerar uma tarefa concluída

Uma tarefa não está concluída simplesmente porque o código foi escrito.

Sempre que aplicável:

- verificar TypeScript;
- verificar lint;
- verificar build;
- testar desktop;
- testar mobile;
- testar estados vazios;
- testar loading;
- testar erro;
- verificar acessibilidade;
- verificar performance;
- verificar regressões.

# 35. Regra principal

Antes de modificar qualquer coisa, Claude deve perguntar:

> "Qual é o menor conjunto de alterações necessário para resolver corretamente esta tarefa sem quebrar o restante do sistema?"

A prioridade é:

1. Correção
2. Manutenibilidade
3. Performance
4. Acessibilidade
5. SEO
6. UX
7. Estética

O resultado deve ser moderno e sofisticado, mas continuar sendo um sistema profissional e sustentável.
